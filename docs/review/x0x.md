# X0X 固件评审：FN ACID 能学什么

日期：2026-10-25。只读调研。X0X 源码快照：`scratchpad/repos/x0x`（下文 `x0x/…`）；FN ACID：`D:\claude\function-acid-fw`（下文 `fa/…`）。

## 0. 先给结论（按对 CPU 负载 / 可用性的影响排序）

| # | 建议 | 影响 | 工作量 | 风险 |
|---|---|---|---|---|
| 1 | 先**测量**：移植 X0X 的周期 / 取指停顿计数器（`fm1_perf.h`）、丢块计数，再做一次“屏幕静止 vs 动画”对比 | 决定后面所有优化往哪打 | 半天 | 低 |
| 2 | 音频热代码约 30 KB，正好等于 32 KB I-cache；把 ISR 热路径放进空着的 RAMTEXT（约 21 KB 空闲），或至少减小热集 | 可能是最大的一项（待 #1 证实） | 1–2 天 | 中 |
| 3 | 存储改成 A/B 双扇区 + **预擦备用扇区**：播放中保存只写页、不擦除，不再卡音；擦除前先把 DMA 缓冲清零 | 可用性大（现在播放中按 SAVE 会卡 / 嗡一声；断电会丢全部槽位） | 1 天 | 低 |
| 4 | MIDI 输出直接从音频 ISR 进 USB 环（X0X 做法），LCD SPI 从 12 MHz 提到 60 MHz | 时钟输出抖动从约 30–50 ms 降到 ≤6 ms；界面帧率翻倍 | 1–2 小时 | 低 |
| 5 | 静音早退：混响 / 延迟输入和线路都为零时跳过（X0X `rv_quiet` / `dl_quiet`）；去掉每块一次的 `fpu_sum(256)` | 安静段落省几个百分点 | 2 小时 | 低 |
| 6 | KEYS 改成按声部、按块渲染，状态放局部变量，包络走控制速率（X0X 303 的写法） | KEYS 曾占 38 %，这是第二大块 | 1 天 | 低–中 |
| 7 | 过载保护（X0X `engine.c:47-90`）：超过 92 % 或均值 85 % 时先砍 KEYS 声部 / 混响 | 防爆音 | 半天 | 低 |
| 8 | 第二核心跑鼓（909/808），以后再考虑 KEYS | X0X 实测最重 pattern 115 % → 68 % | 3–5 天 + 多台实机 | 高 |

## 1. 第二核心

### X0X 怎么做
- **分工**：core 1 渲染 808 + BREAK，core 0 渲染 909 + 两个 303，然后 core 0 等 core 1，做混音、发送效果、母线（`x0x/firmware/src/app/engine.c:598-621` `core2_job`，`:633-717` `render_sub`）。最早是 core 1 = 909 + 808，但 core 1 成了关键路径（core 0 一块里等了 5 ms），后来重新分配（`x0x/docs/plans/2026-10-04-dual-core-and-clock.md:25-31`）。
- **通信**：一个 64 字节对齐的邮箱，每个方向只有一个写者：core 0 写 `fn/arg/check`，再把 `job+1`；core 1 跑完写 `done`；每次读写前后 `csync`（两核共享 cache，不需要 flush）（`x0x/firmware/hal/fm1_cpu1.h:38-47, 159-196`）。core 1 的等待循环在 RAM 的 `.c1_text` 里（`fm1_cpu1.h:59-102`，`x0x/firmware/app.ld:251`），所以空闲时不从 flash 取指；它只在音频中断里干活，写 flash 时中断是关的，所以 flash 关掉时 core 1 不会在跑（`fm1_cpu1.h:23-25`）。
- **调度粒度**：每个“事件之间的片段”交一次活（`render_sub` 在事件之间运行，`engine.c:719-748`），一块里可能交好几次。
- **省了多少**（实测，一台 FM-1）：出厂 loop 43→32 %，五个声部全开 83→53 %，最坏情况 115→81 %；重新分工后 39 / 54 / 68 %，峰值 84 %，不再丢块（`dual-core-and-clock.md:22-31`；`x0x/docs/NEW.md:88`）。
- **代价（这是重点）**：
  - 必须在上电时、音频和定时器之前启动，晚启动 core 1 进不了入口（`dual-core-and-clock.md:10-11`，`main_fm1.c:447-450`）。
  - core 1 经过芯片 ROM 启动，PC 限制要临时打开（`plat_fm1.c:123-141`）。
  - 栈要给 `usp`（rti 之后用的是 usp），一开始给 256 B 就把 X0X 的变量踩坏了（`dual-core-and-clock.md:14-16`）。
  - **有些 FM-1 的 core 1 会读错内存**（读到 0x00200000），需要校验字 + 计数，坏了就永久降为单核（`fm1_cpu1.h:14-21, 176-196`；`NEW.md:57-66`）。
  - 必须把 VDC14 / SYSVDD 提到 M-VAVE 原厂的 1.60 V / 1.38 V，否则有的机器双核满载时读错 flash 和 SRAM 而崩溃（`x0x/firmware/hal/fm1_sys.h:82-108`，`main_fm1.c:389-392`，`NEW.md:22-24, 37-41`）。
  - core 1 崩溃时故障处理跑在 core 1 上，不能 reboot（会把自己 hold 住冻死），只记录然后让 core 0 超时放弃（`x0x/firmware/hal/fm1_irq.h` 中 `core` 字段那段）；崩过一次就写 `.noinit` 标记，到断电前都用单核（`fm1_cpu1.h:52-56`，`main_fm1.c:442-446`）。
  - 前后参考了 Melodee、Jangada 两个项目和多位测试者的实机数据，版本 1.0.2–1.0.9 都在修它。

### FN ACID 现状
单核。一个 ISR（`fa/firmware/src/platform.c:229-252`）里先按步沿分段渲染鼓（`fa/firmware/src/dinghy.c:1501-1517`），然后一个每采样的大循环把其余所有东西算完（`dinghy.c:1519-1680`）。

### 差距与建议
- 我们的鼓**已经**是“先找这一块的步沿、再分段渲染进 `drBuf`”的结构（`dinghy.c:1505-1516`），这正是 X0X 交给 core 1 的那种独立任务。改法：把 `dk_render` 的分段交给 core 1，core 0 同时跑每采样循环；循环里先不加 `drBuf[i]`，把加饱和前的总和写进一个 int 缓冲，等 core 1 完成后再做第二遍（加鼓 → `sat` → punch-in / 滤波 / crush）。808 最重（X0X 主机测量 808 密集 171 ns/采样，909 54 ns，`x0x/docs/plans/2026-10-04-performance.md:157-160`），收益在用 808 的歌里最大。
- KEYS 也能拆，但它每采样要用 `E.duck`（kick 算出来的），要先改成块级 duck 曲线，建议放第二步。
- **工作量 / 风险**：移植 `fm1_cpu1.{h,S}`、`app.ld` 的 `.c1_text`、`crt0` 拷贝、`build.py` 把 `.c1text.bin` 打进镜像、`fm1_guard_pc_open`、电压提升、core 1 故障处理、单核回退和开关。3–5 天编码，**必须多台实机长时间测**。高风险：坏机器上会崩，只是能自动退回单核。建议排在 #1–#7 之后，等确认单核优化到头了再做。
- **单独值得先拿的一件**：电压提升（`fm1_sys.h:82-108` 两个函数 + `main_fm1.c:389-392` 四行）。X0X 说的是“负载下有的机器读错 flash/SRAM”，单核重负载也可能碰到。约 20 行，风险低（就是原厂固件的电压）。

## 2. 热代码 / 数据放哪、块大小、采样格式、CPU 怎么测

### X0X
- **内存布局**和我们一样来自 Felucca：代码和常量都在 XIP（`x0x/firmware/app.ld:240-249`）；`.ram_text` 只放 flash 驱动，`.c1_text` 放 core 1 等待循环。**X0X 没有把 DSP 放进 RAM**；这一项写在它的计划里但没做，条件是“如果负载随界面活动跳变”（`performance.md:260-261`）。
- **编译**：DSP、音序器、引擎是单独的编译单元，用 `-O2`；UI 用 `-Os`（`x0x/tools/build.py:39-45, 229-240`）。单精度 FPU，`-ffp-contract=off`。
- **块大小**：I2S 半缓冲 512 帧（11.6 ms），每次 `engine_render` 256 帧（`main_fm1.c:10-15, 47-53`）。理由：一个重步会集中在一块里，加倍半缓冲把它摊开，只多一块延迟（`main_fm1.c:10-12`）。
- **采样格式**：内部 float，出口转 int32（`engine.c:754-763`）。
- **CPU 测量**：
  - 每块用 TIMER4（24 MHz）计时，`cpu_q8` 指数平均，另记峰值（`main_fm1.c:38-83`）。
  - **丢块检测**：渲染完如果 DMA 已经走到下一半，`xruns++`（`main_fm1.c:93-99`）。
  - 每阶段计时 `eng_prof[]`（`engine.c:15-19`），PERF 页显示每个部分的占比。
  - **周期计数器 + 取指 / 读 / 写停顿计数器**（`x0x/firmware/hal/fm1_perf.h`，来自 JieLi SDK 的 corex2 寄存器；`DBG_CON` bits 0-2 打开），PERF 页可以显示 “STALLS FETCH x % READ y % WRITE z %”（`x0x/firmware/src/app/ui.c:1352-1390, 3497-3504`）。
  - IRQ 栈水位（`plat_fm1.c:166-185`）。
  - 实测主频 **360 MHz**，没有超频余地（`dual-core-and-clock.md:101-110`）。
  - 可以拿来换算的数据：出厂 loop 单核 43 %（512 帧块）≈ 3510 周期/采样，对应 Mac 上 1221 条指令/采样，也就是**每条主机指令约 2.9 个设备周期**（`dual-core-and-clock.md:22`，`performance.md:241`）。

### FN ACID
- 块 256 帧（5.8 ms）（`fa/firmware/src/platform.c:63`），整半渲染。
- 整个固件是一个编译单元，全部 `-Os`（`fa/tools/build.py:40-42, 158-163`），**包括我们原样引入的 drum909.c / drum808.c**（`dinghy.c:23-25`），而 X0X 是用 `-O2` 编它们的。
- 实测 hot set（`fa/build/syms.txt`，当前构建）：`fm1_alnk0_irq` 8660 B（app_audio、kv_run、reverb 都内联进去了）、`control` 2402、`eval_acid0` 1510、`eval_bio` 952、`sg_lanes` 858、`zoo_eval` 836、`midi_step` 486、`eval_win` 356、`cutoff_at` 276、`eval_kick` 288，加上 `d9_render` 8928 或 `d8_render` 10882、鼓的 trigger / 包络辅助函数、`usb_poll` 2332 / `uac_service` 404 / `uac_tap` 152 ……，每块实际要跑的代码约 **28–31 KB**，几乎正好是 32 KB I-cache。块与块之间 UI（`app_main` 18 KB + 绘图函数）又会把它挤出去。
- RAMTEXT 区 24 KB（`fa/firmware/app.ld:14`），现在只用 0xB20 = 2.8 KB（`_rt_end`，syms.txt），**约 21 KB 空着**；0x01C06000–0x01C08000 还有 8 KB“调试用”空间。RAM（.data + .bss）已用 95.4 / 96 KB，pool 319 / 336 KB，那边都很紧。
- 负载 40 % ≈ 2.32 ms/块 ≈ 3260 周期/采样（按 360 MHz 算）。
- 计时：`cpu_us`/`cpu_avg8`/`cpu_max` 加分段 profile（`dinghy.c:1415-1420, 1685-1689`）；**没有丢块计数**，没有停顿计数器，没有 IRQ 栈水位。
- 反汇编里每采样路径上有硬件除法：梯形滤波软削波的 `u3 / 3`（ACID 和第二个 303 各一次，`dinghy.c:1561, 1584`，在 `build/dinghy.dis` 0x200e0a2 / 0x200e1bc 是 `r5 = r5 / r6 (s)`），还有 `wet += (b * V2.send) / 100`（`dinghy.c:1588`）。`-Os` 下 clang 没有把常数除法换成乘法。整个 ISR 里一共 16 条除法指令。
- 每块还跑一次 `fpu_sum(256)`（`dinghy.c:1681-1684`），这是 0.34 版留下的 FPU 自检。

### 差距与建议
1. **先测（半天，低风险）**：原样移植 `fm1_perf.h`，在 GLO 第 1 页显示每块周期数和 FETCH 停顿百分比；移植丢块检测（`main_fm1.c:93-99` 那 5 行）。再按 X0X 列的第 2 步做实验（`performance.md:265-271`）：同一首歌，屏幕静止 vs 转旋钮 / 动画，对比负载。差距大就说明是 I-cache 问题。
2. **如果是取指停顿**（1–2 天，中风险）：
   - 加一个新段（比如 `.fast_text`），放进 RAMTEXT 剩下的约 21 KB，放 `fm1_alnk0_irq`（8.7 KB）+ `control` + `eval_*`（约 6 KB）。注意 `build.py` 现在检查 `.ram_text` 里不能有 call（`fa/tools/build.py:203-207`），那条规则只适用于 flash 驱动；新段要单独处理。XIP 和 RAM 之间超出 call 的跳转范围（`fm1_flash.h` 的 `FL_FAR` 注释），所以 RAM 里的代码调 XIP 函数（`d9_render`、`kv_start`……）要用函数指针，或者把这些函数也放进来。先拿 `kv_run` + reverb + 梯形滤波做一个小实验，看负载降多少，再决定要不要搬全部。
   - 把热查表（`SINT` 2 KB、`INC64` 3 KB、`BIO_WT` 2 KB，`fa/firmware/src/acid_tables.h:29, 118, 217`）也放到 RAMTEXT 区（rwx），不占已经很紧的 96 KB RAM。
3. **`-O2` 编 DSP**（1–2 小时，低风险，需要实测）：把 drum909.c / drum808.c 改成单独的 `-O2` 目标文件（它们本来就自成一体，X0X 就是这么编的）。注意 `-O2` 代码更大，如果瓶颈是 I-cache，可能不升反降，一定要用 #1 的计数器 A/B 对比。
4. **小修**（30 分钟）：`u3 / 3` 改成 `(u3 * 21845) >> 16`，`/ 100` 改成预先算好的 Q15 增益；`fpu_sum(256)` 改成只在 GLO 页打开时跑，或者每 64 块跑一次。
5. **块大小**：40 % 的平均值暂时不需要 512 帧。如果加了丢块计数后发现有偶发丢块（重步、换歌时 `drum_apply` 那种），再考虑。要改的话，USB 音频环的水位（`fa/firmware/src/usb.c:63-85`）也要一起调。

## 3. 303：X0X `bass303.c` vs 我们的梯形滤波

### X0X
- Open303 的 C99 / float / 不用 libm 移植，加 Devilfish 的参数范围和 Soft / RAT 失真（`x0x/firmware/src/dsp/bass303.h:1-31`）。
- 信号链：polyBLEP 锯齿或 tanh 塑形方波 → 高通 → TeeBeeFilter（4 极，反馈经过一个高通）→ 半带抽取 → 14 Hz 全通 / 24 Hz 高通 / 7.5 Hz 陷波 → 200 Hz 去咔嗒的幅度包络 → 可选失真（`bass303.c:513-679`，失真 `:458-509`）。
- **2 倍过采样**（多相 IIR 半带，6 个系数，`bass303.c:401-419`）；**控制速率每 4 个采样**，包络递推用闭式精确推进、系数线性插值（`bass303.h:53-62`，`bass303.c:540-585`）。
- 每块把热状态拷进局部变量再循环（`bass303.c:516-534`：“out[] may alias the struct's floats, which would force reloads”）。
- 空闲：门关、幅度低于 −120 dB 并持续 500 ms 后只输出零，振荡器和包络在块级闭式推进（`bass303.c:681-729, 435-456`）。
- 过载保护的 “lite” 模式：关掉过采样（`bass303.c:524-530`）。
- **代价**：一个 303 在 Mac 上 71 ns/采样，是整个 909 的三倍多（`performance.md:171-173`）；其中过采样 24 ns，失真 21 ns。代码 11 KB，`bass303_render` 7.2 KB（`performance.md:183-185`）。按 2.9 周期/主机指令估算，一个 303 在设备上大约占 25–30 % 的单核 CPU。

### FN ACID
Q15 整数 4 极梯形滤波，每采样一次三次多项式软削波，参数每 16 采样在 `control()` 里更新（`dinghy.c:1554-1567`；第二个 303 `:1577-1590`）。每采样的成本是 X0X 的一小部分。

### 差距与建议
- **CPU 上我们已经很省，不建议换成 X0X 的 303。** 音色上的差距在别的地方：X0X 有 polyBLEP（我们的裸锯齿在高音会有混叠）、反馈高通（303 低音变薄的关键）、accent 的 RC 跟随器、200 Hz 去咔嗒。
- 可以借的、几乎不花 CPU 的东西：
  1. **反馈路径加一个一阶高通**（TeeBeeFilter 的 `fbhp`，`bass303.c:626-629`）：每采样多 2 次乘法，共振时低频更像 303。整数实现约 10 行。
  2. **控制速率参数线性插值**（`bass303.c:572-583`）：我们每 16 采样跳一次 `E.g`，快速包络扫频可能有拉链声；插值每采样只多一次加法。
  3. **空闲早退**：ACID / V2 已经有 `amp > 8` 门控，但滤波状态和相位还在每采样更新；可以学 X0X，静音 N 毫秒后整段跳过。
- 工作量：每项 1–2 小时；风险低（但要用耳朵听）。

## 4. 发送效果 / 母线（`fxbus.c`、`master.c`）

### X0X
- **混响**：4 个梳状 + 2 个全通（Freeverb 调音，和我们同源），梳状线是 int16、环路量化到 12 bit，有阻尼，发送前有高通；立体声：右声道用交替符号读梳状、自己的两个全通（`x0x/firmware/src/dsp/fxbus.c:179-251`）。
- **延迟**：拍子同步，时间变化时慢慢滑过去；反馈经过一阶低通；DIGI / TAPE 两种（TAPE 有 wow/flutter、环路饱和）；乒乓（`fxbus.c:278-394`）。
- **两者都有空闲检测**：混响输入和所有梳状写入连续 `1356+8192` 个采样都为零 → 整块跳过（`fxbus.c:9, 181-187, 248`）；延迟线全零、输入为零 → 只推进写指针（`fxbus.c:283-307`）。
- 母线：压缩器每 4 个采样算一次增益（`master.h` 的 `MST_CR 4`），限幅器 64 采样前瞻，用一个跟着更新的倒数代替每采样除法（`master.h` 中 `la[MST_LA]`、`inv_env`；`performance.md:212-216`）。
- 代价：FX 20–30 ns/采样，母线约 25 ns（`performance.md:164-165`）。

### FN ACID
- 混响：同一套 Freeverb 调音，int16、单声道、整数（`dinghy.c:884-910`）；**只要 `P.rMix != 0` 就每采样都跑**，不管有没有输入（`dinghy.c:1624`）。
- 延迟：每采样读写两条 int16 线（`dinghy.c:1618-1622`），**一直在跑**。
- 母线：`sat()` 多项式（`dinghy.c:949-956, 1625`），没有压缩器 / 限幅器。

### 差距与建议
- **加空闲早退**（2 小时，低风险）：学 `fxbus.c:181-187, 248`，记“连续多少采样输入为零且写回为零”，超过梳状最长长度 + 尾巴时跳过 `reverb()`；延迟线同理（`wet == 0` 且反馈写回为零）。在只有鼓（鼓不进延迟）或停止的时候能省一截。我们的 FX 是在每采样循环里做的，需要一个“这一采样跳过 FX”的分支，或者把 FX 挪到循环外按块做（见 #6 的块化）。
- 其他不需要改：我们的整数 FX 已经比 X0X 的 float 版便宜。

## 5. 音序器、数据模型、存储

### X0X
- **数据模型**：32 个 pattern，每个包含 909、808（各 11 轨，最多 64 步，按位存）、两条 303（64 步，每步 note + flags）、BREAK；不含指针，可以直接赋值（`x0x/firmware/src/seq/pattern.h:12-77`）。歌曲 192 小节，每小节记每个声部的 pattern、静音、重复 1–8 次（`sequencer.h:52, 69-77`）。运动轨 160 条，每条 64 步，按 pattern × 参数分配（`motion.h:25-36`）。还有步概率 / 条件触发、undo / redo（`undo.c`）。
- **调度**：每块先算到下一个事件还有多少采样（`sequencer.c:426-441` `seq_until_event`），渲染到那里，再触发事件（`seq_advance`，`:443-519`），所以是采样级精确；外部时钟按采样数测 tick 间隔，1/8 平滑（`:395-424`）。
- **存储**：每个对象一对 A/B 扇区；保存写**另一份**：擦除 → 写内容 → 最后写 32 字节头（带序号和 CRC）。加载时取有效且序号最高的那份，断电写坏只会退回上一次（`x0x/firmware/src/storage.c:4-14, 85-105, 138-174`）。写完回读校验（`:167-172`）。
- pattern + 歌曲 + 运动轨（约 30 KB，大部分是空步）用 LZ 压缩成一个流，分到 4 个对象里；流头带原始长度和 CRC，跨对象写坏时尝试旧份的组合（`x0x/firmware/src/app/project.c:1-15`）。**只写内容变了的对象**（FNV 哈希，`project.c:64-66`），自动保存一般只擦 1–2 个扇区。
- flash 占用：设置 2 × 4 KB（0xFC000），sound / pat0 / pat1 / song 各 2 × 4 KB（0x97000–0x9F000），面板校准、运动轨各 2 × 4 KB（0xDC000–0xDFFFF）：共 14 个扇区，56 KB（`storage.c:20-23, 50-61`）。
- **X0X 也没有做到“保存不卡音”**：擦除时中断关闭，它先 `audio_silence()` 把 DMA 缓冲清零，免得 DMA 循环播放旧数据（`x0x/firmware/src/x0x.c:68-75`，`main_fm1.c:112-117`）。它的做法是**播放中不保存**：播放时按 SAVE 显示 “SAVES WHEN STOPPED”，停下后再存（`ui.c:1319-1338`）；自动保存只在停止、4 秒没有操作、距上次至少 20 秒时进行（`ui.c:4588-4617`）。
- **备份 / 恢复**：通过 USB SysEx 把整个项目导出成文件，可以导回；恢复时先暂存到 A/B 的另一份（不写头），全部收到并校验后在屏幕上确认，再用一条日志记录原子提交，断电后下次开机补完（`x0x/firmware/src/backup.c:1-50`）。网页工具 `web/backup`。

### FN ACID
- 一个 4 KiB 扇区，`store_t = {cur; slot[6]; used[8]}`（`dinghy.c:75-79`），擦除 → 写内容 → 最后写头（`platform.c:161-172`）。**只有一份**：擦完、写头之前断电 = 头无效 = 加载失败 = 回到默认值，6 个用户槽全丢。
- 自动保存：停止且 20 秒没改才存（`dinghy.c:3141`），这一点没问题。但 **SAVE 按钮（`dinghy.c:2378`）和长按存槽（`:2309`）在播放中也会直接 `save_all()`**，擦除约 50 ms 中断全关；而且我们擦除前**没有清 DMA 缓冲**，DMA 会把最后一个 5.8 ms 的半缓冲循环播放，听起来是“嗡”一声，不是静音。

### 差距与建议
1. **擦除前清零 DMA 缓冲**（10 分钟，零风险）：`settings_save` 和 `ota_erase` 调 `fl_erase4k` 之前把 `abuf` 清零（照抄 `x0x/firmware/src/x0x.c:68-75`）。嗡声变成一小段静音。
2. **A/B 双扇区 + 序号**（半天，低风险）：照 `storage.c` 的头格式改，`SETTINGS_AT` 加一个相邻扇区（`0xFD000` 在 Felucca 的 globals 区 `FL_GLOB_LO..HI` 里，要确认没被别的东西用）。断电不再丢槽位。
3. **播放中保存不卡音：预擦**（半天，低–中风险）。关键是 `fl_write` 已经按 256 字节页分块、每页之间会重新开中断（`fa/firmware/hal/fm1_flash.h` 的 `fl_write`），只有 4 KB 擦除（约 50 ms）是一整段关中断。所以：
   - 每次保存后（或开机、停止时）把**下一次要写的那份**预先擦好；
   - 播放中保存只做页编程：16 页，每页关中断约 0.5–1 ms（`fl_prog_ram` 最长等 10 ms，一般 <1 ms）。我们的渲染平均 2.3 ms / 5.8 ms，晚 1 ms 还在预算内；为了更稳，可以每次主循环只写一页。
   - 写前用 `fl_rdsr` 或读回确认那份确实已擦（全 0xFF），否则退回“停止后再存”（X0X 的做法）。
4. 以后如果要存多首歌 / pattern 库，再学 X0X 的 LZ 压缩流和“只写改过的对象”。

## 6. MIDI 与 USB 音频

### X0X
- **输入**：USB 和 TRS（UART1 + DMA 环，`x0x/firmware/src/midi_uart.c:1-7`）进同一个队列；**音频 ISR 在每块开头取出来处理**（`engine.c:484-506`）：时钟 / 开始 / 停止 / 继续，按通道把音符给各个声部（GM 鼓音符给 909/808，音符给 303，重叠音符 = 滑音，36–43 给 BREAK 切片）（`engine.c:447-482`）。没有 CC 输入 / 输出。
- **时钟输入**：在采样域测 tick 间隔（`ext_since`，1/8 平滑），时钟停 0.5 s 后回到内部时钟（`sequencer.c:395-424, 446-454`）。
- **时钟 / 音符输出**：音序器在采样级位置发出（`sequencer.c:514-517`），`midi_out_event` 在**音频 ISR 里**直接进 USB 环（`x0x/firmware/src/usb.c:133-140`），TIMER5 每 0.5 ms 在渲染之外 `usb_poll`（`main_fm1.c:135-151`）。抖动不超过一块（11.6 ms）+ 0.5 ms。
- **USB 音频**：设备 I2S 时钟实测约 44,145 Hz；X0X 用三次插值重采样，严格按 44.1 kHz 发，宿主看不到时钟漂移（`usb.c:50-70`）。

### FN ACID
- 输入：主循环 `midi_get`，**只处理时钟 / 开始 / 停止**，而且只在 CLOCK = IN 时处理；音符输入全部丢掉（`dinghy.c:3091-3108`，`continue` 在 `:3095`）。速度用主循环的 `fm1_ms` 时间戳估算（1 ms 分辨率），步进锁 tick（`clk_adv`，`dinghy.c:1196-1208`）。
- 输出：ISR 写进 `mqOut`（`dinghy.c:958-966`），**主循环再转发到 USB**（`dinghy.c:3090`）。而主循环在每帧画屏时会卡在 `lcd_sync()` 等 DMA：环形 134×170 + 示波 106×170 = 81.6 KB/帧，在 12 MHz SPI（`fa/firmware/src/lcd.c:10`）下要约 54 ms。所以**时钟输出会成堆发出，抖动约 30–50 ms**，外部设备跟我们同步会不稳。时钟输入的 tick 计数也在主循环里，同样受影响。
- 有 CC 输出（`dinghy.c:1269-1280`），X0X 没有。USB 音频支持 48 kHz（我们比 X0X 多），44.1 kHz 时用 ±1 帧的方式处理漂移（`fa/firmware/src/usb.c:63-72`）。

### 差距与建议
1. **MIDI 输出直接从 ISR 进 USB 环**（30 分钟，低风险）：`mq_push` 里直接调 `midi_out_event((st >> 4) | st << 8 | d1 << 16 | d2 << 24)`，删掉主循环 `dinghy.c:3090` 的转发。`midi_out_event` 注释写的就是“from the audio ISR”，只要保证所有 `mq_push` 都在 ISR 上下文里调用（单一生产者）。抖动降到 ≤ 5.8 ms。
2. **LCD 提到 60 MHz**（1 行，低风险）：`lcd.c:10` 的 `LCD_BAUD 4u` 改成 `0u`。X0X 在很多台机器上用的就是 0（实际约 44 MHz，`x0x/firmware/src/lcd.c:9-14`），一帧从约 54 ms 降到约 15 ms，主循环被卡的时间少了，界面也更跟手。
3. **时钟输入放进 ISR**（2 小时）：ISR 每块开头从 `midi_in_q` 取 F8 / FA / FC，按块内采样计数（照 `sequencer.c:395-424`），速度用采样数算，`P.bpm` 不再被截成整数。
4. **音符输入**（半天）：ACID / ZOO / KEYS / 鼓按通道接受音符输入（照 `engine.c:447-482`，GM 鼓音符表直接拿来）。外接键盘、DAW 都能直接用。
5. **TRS MIDI 输入**（半天，低风险，`midi_uart.c` + `hal/fm1_uart.h` 原样移植，在 TIMER5 里轮询）。
6. USB 音频重采样：只有用户反馈 AU 宿主有爆音时再做，优先级低。

## 7. 界面绘制

### X0X
- 没有整屏帧缓冲，用 240×144 的条带画布，画完一次 DMA 发出（`x0x/firmware/src/gfx.c:1-20`）。DMA 发出后主循环继续干活，下次用到缓冲时才等（`lcd.c:1-7, 26-33`）。
- 主循环约 60 帧/秒（16 ms），每帧之间只读输入（`main_fm1.c:535-541`）。
- **只发变了的部分**：每个区域对画布做 FNV 哈希，没变就不发（`ui.c:2583-2597`）；主区域按行和 8 像素列块分别哈希，只把变了的矩形挤到画布前面、一次发出。注释写明：面板没有 TE 线，整个区域要 18 ms，比面板刷新慢，所以会撕裂；只发变化的两列约 3 ms（`ui.c:2599-2662`）。
- SPI 60 MHz（`lcd.c:9-14`）。

### FN ACID
- 同样的条带 + 异步 DMA（我们的 `lcd.c` 和 X0X 的只差 `LCD_BAUD`）。环形 + 示波每 33 ms 重画（`dinghy.c:3123-3133`），顶栏每 100 ms；**每次整块发出**，12 MHz。实际帧率被 SPI 卡在约 18 fps，主循环大部分时间在 `lcd_sync()` 里空转。

### 差距与建议
- `LCD_BAUD 0`（见 6.2），收益最大、改动最小。
- 环形图每帧变化的只有播放头附近和几个点：可以照搬 `cv_commit_rect`（`ui.c:2605-2662`，约 60 行）只发变化的矩形，撕裂和 SPI 时间都会降。示波器每帧都变，照常发。
- 对音频 CPU 的影响是间接的：绘图代码（`sim303`、`spectrum` 等）和音频共用 I-cache。等 #1 的“屏幕静止 vs 动画”实验做完，如果差别明显，可以把示波 / 频谱降到 15 fps。
